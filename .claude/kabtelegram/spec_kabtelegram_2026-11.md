# Spec: вход через Telegram прямо в Moodle (`auth_kabtelegram`), 24.11.2026

## Зачем

WordPress kabacademy.com закрывается к концу недели (~29.11.2026), мост Edwiser WP→Moodle
выключается на этой неделе. Сейчас кнопка «Войти через Telegram» на странице входа Moodle
(`auth_telegram_wp`) уводит на WordPress: там `wptelegram-login` + `kab-telegram-bridge`
логинят в WP, а сессию Moodle поднимает Edwiser SSO. Без WP и Edwiser кнопка мертва.

Слово владельца: «если можно сделать вход через Telegram на Moodle — давай сделаем; если сложно —
можно вообще убрать». Делаем: протокол Telegram Login открыт и прост (подпись HMAC-SHA256),
бот входа свой (@kabacademy_login_bot).

## Решение: отдельный auth-плагин `auth_kabtelegram`, а не расширение `auth_kabmagic`

- **Свой выключатель.** Telegram — внешняя зависимость со своими отказами (домен бота в BotFather,
  токен, доступность oauth.telegram.org из России). Отдельный плагин выключается в «Управлении
  аутентификацией» одним глазом, не трогая вход по ссылке на почту, на котором стоят ~55 тыс.
  аккаунтов без пароля и письма `local_kabsignup` (`issue_link()`).
- **Свой порядок кнопки** на странице входа (порядок = порядок включённых методов).
- **`auth_kabmagic` на проде и под нагрузкой** — его код не трогаем вовсе.
- Связь с `auth_kabmagic` только мягкая: ссылка на его `request.php` для «неизвестного Telegram»
  (если он включён) и, если класс есть, его фильтр `is_subresource_url()` для `wantsurl`.
  Жёсткой зависимости (`$plugin->dependencies`) нет.

## Как устроен вход (протокол Telegram Login, режим redirect)

Виджет Telegram (`telegram-widget.js`) в режиме без всплывающего окна открывает
`https://oauth.telegram.org/auth?bot_id=<id>&origin=<origin>&return_to=<url>`, а после подтверждения
Telegram возвращает браузер на `return_to#tgAuthResult=<base64url JSON>`. JSON — поля
`id, first_name, last_name, username, photo_url, auth_date, hash` (пустые не приходят).
Проверка по документации Telegram («Checking authorization»):
`data_check_string` = все поля, кроме `hash`, как `key=value`, по алфавиту, через `\n`;
`secret_key = SHA256(bot_token)`; `hash == hex(HMAC_SHA256(data_check_string, secret_key))`.
Виджет на нашей странице не нужен: кнопка ведёт сразу на oauth.telegram.org, как старый скрипт в
подвале. Это одна полная страница вместо всплывающего окна — работает и на телефоне.

Потоки:

**A. Вход.** Кнопка «Войти через Telegram» (`loginpage_idp_list`, видна, только если задан токен) →
`auth/kabtelegram/start.php?wantsurl=…` → в `$SESSION` кладётся `state` (16 случайных байт),
режим `login`, `wantsurl`, время → редирект на oauth.telegram.org с
`return_to = …/auth/kabtelegram/callback.php?state=<state>` → Telegram → `callback.php` (GET):
страница сама читает `#tgAuthResult` скриптом, стирает его из адресной строки и отправляет POST
(`tgauth`, `state`, `sesskey`) → сервер:
1. `sesskey`; `state` совпадает с сессией (`hash_equals`), не старше 30 минут, одноразовый (стирается);
2. подпись верна, `auth_date` не старше настройки `maxage` (по умолчанию 60 мин, максимум сутки) и
   не из будущего (допуск 5 мин);
3. привязка `tgid → userid` есть; аккаунт жив, подтверждён, не заблокирован, локальный, не гость,
   метод аутентификации из настройки `allowedauths` (по умолчанию `manual,email`) и включён;
4. `auth_date` строго больше последнего принятого для этой привязки (`lastauthdate`) — повтор
   того же ответа Telegram не впускает;
5. `complete_user_login()`, лимит одновременных сессий, cookie логина, редирект на `wantsurl`
   (только внутри `wwwroot`, без картинок/стилей), иначе `/my/`.

**B. Неизвестный Telegram.** Подпись верна, но привязки нет → аккаунт **не создаётся**. Проверенный
Telegram запоминается в сессии на 30 минут («ожидает привязки»), страница объясняет: «Этот Telegram
ещё не привязан. Войдите по ссылке на почту (или с паролем) — и привяжем». Кнопки ведут на
`auth/kabmagic/request.php?wantsurl=<link.php>` (если вход по ссылке включён) и на страницу входа
с тем же `wantsurl`. После входа человек попадает на `link.php`, видит «Привязать Telegram
<имя / @username> к аккаунту <ФИО, почта>?» и подтверждает кнопкой (POST + `sesskey`).
Автопривязки без подтверждения нет: на общем компьютере следующий человек не получит чужой Telegram
молча.

**C. Привязка из профиля.** «Настройки → Учётная запись → Вход через Telegram» (`link.php`, хук
`extend_navigation_user_settings`, только свои настройки): статус привязки, «Привязать Telegram»
(`start.php?mode=link` → тот же круг через Telegram, `state` привязан к `userid`) или «Отвязать»
(POST + `sesskey`). Telegram, привязанный к другому аккаунту, не перепривязывается — сообщение
«уже привязан к другому аккаунту» (только тому, кто сам только что вошёл в этот Telegram).

**D. Импорт 132 привязок из WP.** Разовая операция владельца плагина, не код плагина: выгрузка
`wp_usermeta` (`wptelegram_user_id`, `wptelegram_username`, `wptelegram_first_name`, `moodle_user_id`)
с e-mail WP-пользователя → сопоставление с `mdl_user`: по `moodle_user_id` (связка Edwiser) **и**
совпадению e-mail (без учёта регистра); если связка указывает на аккаунт с другой почтой — по почте;
неоднозначные и ненайденные — в отчёт, не импортируются. Вставка в `auth_kabtelegram_links` с
`source = 'wp'`. Скрипт — `tools/kabtelegram-import/` (без данных и адресов серверов); выгрузки
живут только в рабочей папке сессии и удаляются после импорта, данные людей в репозиторий не кладём.
Сухой прогон 24.11.2026: 132 из 132 сошлись по связке и почте, все аккаунты живые, `manual`/`email`.

## Изоляция

- `user_login()` всегда `false`; `is_internal()`, `can_change_password()`, `can_reset_password()`,
  `can_signup()`, `can_confirm()`, `can_be_manually_set()`, `prevent_local_passwords()` → `false`.
- Пароли и `auth` пользователей не трогаются; у плагина нет «своих» пользователей.
- Аккаунты не создаются никогда (ни при входе, ни при привязке).
- Свои данные — одна таблица `auth_kabtelegram_links`; чужих таблиц не пишет.
- Ядро и тема не патчатся: кнопка — штатный `loginpage_idp_list()`, пункт настроек — штатный хук.
- `auth_kabmagic` не меняется. `auth_telegram_wp` и `auth_edwiserbridge` выключены на проде 24.11.2026
  в 14:31 основной сессией (`auth = email,webservice,kabtarget,kabmagic`), служба моста Edwiser
  выключена; обратно `auth_telegram_wp` не включать. Каталог пока остаётся.

## Внешние зависимости

| Что | Зачем | Если сломается |
|---|---|---|
| Бот @kabacademy_login_bot, его токен (настройка `bottoken`, вводит владелец) | подпись ответов Telegram; `bot_id` = число до `:` в токене | без токена кнопки нет; неверный токен — «подпись не сошлась», никто не входит |
| Домен бота в BotFather (`/setdomain`) = домен Moodle (`edu.kabacademy.com`) | oauth.telegram.org пускает только с origin домена бота | «Bot domain invalid» на странице Telegram; у одного бота один домен — после смены WP-вход через Telegram перестаёт работать (WP и так закрывается) |
| oauth.telegram.org доступен из браузера пользователя | сама авторизация | в РФ Telegram местами режут — остаются ссылка на почту и пароль |
| `auth_kabmagic` (мягко) | путь «неизвестный Telegram → вход по почте → привязка» | если выключен — кнопка только «Войти с паролем» |

На dev (`dev-edu.kabacademy.com`) настоящий Telegram не проверить: у бота один домен, и он нужен
проду. На dev проверяется всё, кроме страницы Telegram: тестовый токен и подписанные им ответы
подкладываются в `callback.php` так же, как это сделал бы Telegram.

## Таблица `auth_kabtelegram_links`

| Поле | Тип | Что |
|---|---|---|
| `userid` | int, unique | аккаунт Moodle |
| `tgid` | int(20), unique | id пользователя Telegram |
| `tgusername` | char(64) | @username на момент последнего входа/привязки, может быть пустым |
| `tgname` | char(255) | имя и фамилия из Telegram (для показа «к какому Telegram привязан») |
| `source` | char(10) | `wp` — импорт, `user` — привязал сам |
| `lastauthdate` | int | последний принятый `auth_date` (защита от повтора) |
| `timecreated`, `timemodified`, `timelastlogin` | int | — |

Удаление пользователя — наблюдатель `\core\event\user_deleted` удаляет его привязку. Privacy API:
экспорт и удаление привязки.

## Что делает владелец (не код)

1. Токен бота — в настройки плагина (Плагины → Аутентификация → Вход через Telegram). Токен — в
   BotFather (`/token`) или на странице настроек WP Telegram Login на WordPress, пока он жив.
2. BotFather → `/setdomain` → @kabacademy_login_bot → `edu.kabacademy.com` (сейчас `kabacademy.com`).
3. «Управление аутентификацией»: включить «Вход через Telegram» (MFA). «Telegram через WordPress»
   уже выключен (24.11.2026).

Подвал (`additionalhtmlfooter`) с мёртвым скриптом «Вход через Telegram» правит основная сессия
переноса витрины, не этот плагин: скрипт вложен в незакрытый `<script>` «CUSTOM TOGGLE COURSES»,
весь блок падает на каждой странице, и удалять его можно только целиком (иначе ломается следующий
скрипт фильтров значков). Плагину код в подвале не нужен; если когда-нибудь понадобится — отдельным
закрытым `<script>` и только после той правки.

Порядок в день переключения: плагин на проде (выключен) → импорт привязок → токен → `/setdomain` →
включить «Вход через Telegram» → проверка входом владельца. До включения на проде входа через
Telegram нет вовсе (старый выключен 24.11).

## Готово

Spec; плагин в ветке и PR; проверка на dev (вход, неизвестный Telegram → привязка, привязка из
профиля, отвязка, повтор ответа, просрочка, чужой `state`, неверная подпись, заблокированный аккаунт);
на проде по слову владельца; строка в реестре CLAUDE.md и в `probe_moodle.sh`
(`auth/kabtelegram/version.php|`); 132 привязки импортированы; старая кнопка выключена (сделано
24.11.2026 основной сессией), подвал — у основной сессии.

## Не входит

- Мобильное приложение Moodle: кнопки `loginpage_idp_list` не-OAuth2 там не работают (как и у
  `auth_kabmagic`); в приложении вход по паролю/ссылке как сейчас.
- Регистрация через Telegram — запрещена, как и на WP.
- Привязка по `request_access=write` (бот не пишет людям) — не запрашиваем.
