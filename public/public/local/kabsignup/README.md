# local_kabsignup — «Запись на курс»

Публичная страница записи на курс для рекламного трафика и витрины: имя, фамилия,
e-mail, телефон → аккаунт (создаётся, если адреса ещё нет) → зачисление на курс →
письмо → страница «спасибо», своя для каждой кампании или курса. Город и страна
проставляются по IP, пол — по имени (`local_kabgender`), возможные дубли аккаунтов
уходят письмом в поддержку, второгодников ловит отчёт секретарю.

Ссылка для лендингов и объявлений:

```
https://edu.kabacademy.com/local/kabsignup/index.php?id=<ID курса>&camp=<метка кампании>&utm_source=…
```

`camp` и `utm_*` не обязательны. UTM-метки и `camp` дописываются к странице «спасибо»,
так что аналитика лендинга продолжает работать после редиректа.

## Поток

1. Курс должен быть в настройке «Курсы с открытой записью», иначе нейтральная
   страница «запись не ведётся» (название курса не раскрывается).
2. Посетитель уже вошёл в аккаунт → зачисляется сразу, без формы, и уезжает на
   «спасибо». Так же замыкается сценарий «войдите и возвращайтесь»: после входа
   Moodle возвращает на эту же страницу. Исключение — админ и преподаватель курса
   (`moodle/course:update`): их не зачисляем, просто показываем «спасибо»
   (удобно смотреть, куда ведёт ссылка, не записывая себя студентом).
3. Гость видит форму: имя (обязательно), фамилия (нет), e-mail (обязательно),
   телефон (обязателен по настройке `phonerequired`, по умолчанию да) + скрытое
   honeypot-поле для ботов.
4. По отправке:
   - **адрес свободен** → создаётся аккаунт (`auth = manual`, `username` = адрес,
     `confirmed = 1`, язык сайта, телефон в `phone1`), сгенерированный пароль,
     зачисление, **автовход** (человек сразу залогинен) и письмо «Вы записаны»
     **с логином и паролем**. Ссылки для входа в этом письме нет: человек уже внутри,
     а ссылка живёт 15 минут и к следующему входу протухнет. Вход по ссылке на почту
     остаётся запасным путём — о нём строка в том же письме;
   - **адрес занят** → по настройке «Если e-mail уже занят»:
     - *записывать сразу* (по умолчанию): зачисляем существующий аккаунт и шлём
       на адрес письмо «Вы записаны» с одноразовой ссылкой для входа (пароль от
       существующего аккаунта мы не знаем и не меняем). Автовхода нет: владение
       адресом не доказано;
     - *просить войти*: страница «у вас уже есть аккаунт» с кнопками «Войти» и
       «Войти по ссылке на почту»; после входа человек возвращается сюда и
       дозаписывается (сценарий из п. 2);
   - **уже записан на этот курс** → страница «Вы уже записаны» (не страница
     кампании) и письмо со ссылкой для входа, если человек не залогинен.
5. Новый аккаунт после ответа обрабатывается фоновой задачей (`after_signup`,
   выполняет cron Moodle): город и страна по IP, проверка на дубль (см. ниже).
6. Редирект на «спасибо». Приоритет: URL кампании (`camp`) → URL курса → общий
   URL из настроек → встроенная `thanks.php` («вы записаны» + кнопка в курс).

## Как это повторяет WordPress

| На WP | Здесь |
|---|---|
| Город, страна по ipinfo.io при заказе (`themes/kabacedemy/inc/ipinfo-moodle.php`) → в Moodle `city`, `country` | фоновая задача: ipinfo.io (токен в настройке `ipinfotoken`; без токена — анонимный лимит ipinfo) или файл GeoLite2 Moodle, если он задан в `geoip2file`. Пишет только в пустые `city`/`country` нового аккаунта, прямо в `mdl_user` без события `user_updated` (иначе Edwiser потащит это обратно в WP) |
| Телефон чекаута → `phone1` в Moodle | поле формы → `phone1` (цифры и ведущий `+`, до 20 символов) |
| Пол по имени (`kab-gender.php` + Moodle `local_kabgender`) | ничего своего: `local_kabgender` слушает `user_created` и проставляет пол сам |
| Пароль из формы чекаута | пароль генерирует плагин и присылает в письме |
| `kab-already-enrolled.php`: повторная запись на бесплатный курс потока не создаёт заказ, показывает «Вы уже записаны»; CompleteRegistration — только за первую запись | статус `already`: своя страница «Вы уже записаны» вместо страницы кампании, пиксель кампании второй раз не срабатывает |
| `kab-dup-alert.php`: новый аккаунт похож на существующий по e-mail или телефону → письмо на support@ | `dupcheck` — те же правила, письмо на адрес из настройки `dupalertto` (support@kabacademy.com) |
| Отчёт «Второгодники ОК» (`tools/repeat_students_report.php` в репо kabacademy.com, cron на web-18) | ничего переносить не надо: отчёт читает БД Moodle и видит все записи в целевой курс с ролью студента, в том числе сделанные этим плагином (ручной метод, роль student). При новом потоке в отчёте меняется `TARGET_COURSE_IDS`, как и раньше |

## Дубли аккаунтов

Принцип «один аккаунт»: дубли сливает только админ вручную, плагин ничего не
сливает и не блокирует запись — только сообщает. Правила (копия `kab-dup-alert.php`
и пакетного аудита `.claude/analysis/account_dedup/` в репо kabacademy.com):

- **e-mail с точностью до точек** в имени ящика, тот же домен (`ivan.petrov@` и `ivanpetrov@`);
- **опечатка в домене**: домен похож на популярный (`gmial.com` → `gmail.com`,
  расстояние Левенштейна ≤ 1 для доменов до 8 символов, иначе ≤ 2), имя ящика то же;
- **то же имя ящика на другом домене** — слабый сигнал; не учитывается для коротких
  (< 5 символов), цифровых и типовых имён (`info`, `anna`, `elena` …);
- **телефон**: последние 9 цифр совпадают с `phone1`/`phone2` другого живого
  аккаунта; мусорные номера (короче 7 цифр, серии, `123456789`) отбрасываются.

Проверяется только новый аккаунт и только против более старых (меньший id) — пара, записавшаяся почти одновременно, даёт одно письмо, а не два. Письмо одно на заявку: в журнале у строки
появляется флаг `dup:<сигналы>`, повторно задача письмо не шлёт.

## Решения и почему

- **Занятый адрес записывается сразу, входа не требуем** (дефолт). «Сначала
  войдите» убивает конверсию рекламного трафика: паролей студенты не знают
  (~55 тыс. аккаунтов заводил Edwiser Bridge), а логин почти ни у кого не равен
  e-mail. Риск невелик: по чужому адресу можно только записать его владельца на
  бесплатный курс — письмо уходит на сам адрес, в аккаунт посторонний не попадает.
  Если захочется строгости — настройка «Просить войти», код менять не надо.
- **Автовход — только для нового аккаунта.** Свежесозданная учётка пуста;
  существующий аккаунт без подтверждения адреса не выдаётся никогда.
- **Логин и пароль — новичку, ссылка — существующему.** Новичок уже вошёл, ему нужен
  способ войти в следующий раз, который не протухнет. Существующему пароль не
  отправить (не знаем) и не сменить (изоляция), поэтому — одноразовая ссылка.
- **Ответ формы одинаков для нового и занятого адреса** (в режиме по умолчанию):
  обе ветки кончаются той же страницей «спасибо», существование адреса в базе
  не светится. Исключение — «уже записан на этот курс»: там видно «вы уже записаны»
  (как на WP; посторонний узнаёт лишь то, что адрес записан на открытый курс).
- **Данные существующего аккаунта не трогаем**, даже пустые телефон и город:
  форму мог заполнить кто угодно, кто знает адрес.
- **Город и дубли — фоном.** Ни ipinfo.io, ни поиск по 56 тыс. аккаунтов не держат
  человека на форме; упадёт ipinfo — запись всё равно состоится.

## Таблица `local_kabsignup_log`

Журнал заявок: рейт-лимит + аналитика по кампаниям. Сам адрес и телефон не хранятся.

| Поле | Что |
|---|---|
| `courseid` | курс из ссылки |
| `userid` | кого записали/нашли |
| `emailhash` | SHA-256 адреса в нижнем регистре (для лимита) |
| `newuser` | 1 — аккаунт создан этой заявкой |
| `campaign` | метка `camp` из ссылки (до 64 симв.) |
| `status` | `created` / `enrolled` / `already` / `loggedin` / `exists` |
| `flags` | итоги фоновой задачи через `;`: `geo` — город/страна записаны, `dup:email,phone` — найдены похожие аккаунты (письмо ушло) |
| `ip`, `timecreated` | откуда и когда |

Статусы: `created` — новый аккаунт; `enrolled` — записан существующий;
`already` — был записан раньше; `loggedin` — записался уже залогиненным;
`exists` — показана страница «войдите» (режим «просить войти»).
Задача очистки раз в сутки удаляет строки старше `retentiondays` (365; 0 — хранить).

## Настройки (Администрирование → Плагины → Локальные плагины → Запись на курс)

| Настройка | По умолчанию | Что |
|---|---|---|
| `courses` | — | по строке на курс: `ID` или `ID|URL страницы «спасибо»`. Только перечисленные курсы доступны для записи |
| `campaigns` | — | по строке: `метка|URL страницы «спасибо»`; метка = параметр `camp`, приоритет над страницей курса |
| `defaultthankyou` | — | общий URL «спасибо», когда у кампании и курса своего нет; пусто — встроенная страница |
| `existingpolicy` | записывать сразу | что делать с занятым адресом (см. выше) |
| `phonerequired` | да | телефон обязателен |
| `ipinfotoken` | — | токен ipinfo.io для города по IP (взять из пула ipinfo в опциях WP). Пусто — анонимные запросы с малым лимитом ipinfo |
| `dupalertto` | support@kabacademy.com | куда писать о возможных дублях; пусто — не писать |
| `ratelimit` | 5 | заявок с одного адреса за окно; на IP — ×10 |
| `ratewindow` | 60 | окно лимита, минут |
| `retentiondays` | 365 | срок хранения журнала, дней; 0 — вечно |

URL «спасибо» — абсолютный `https://…` (страницы на kabacademy.com) или локальный
путь `/…`. Всё остальное молча игнорируется (считается, что URL не задан).

## Изоляция

- **Существующие аккаунты не меняются вообще**: ни пароль, ни `auth`, ни профиль.
  Максимум, что с ними происходит, — ручное зачисление на курс из белого списка
  и письмо со ссылкой для входа (её выдаёт `auth_kabmagic` по своим же правилам).
- Новые аккаунты создаются штатным `user_create_user()` (событие `user_created`
  уходит как обычно — `local_kabgender`, Edwiser и прочие наблюдатели работают штатно).
- Зачисление — штатный метод «Ручная запись» (`enrol_manual`) с ролью инстанса;
  если инстанса в курсе нет, создаётся дефолтный. Выключенный инстанс не
  включается молча: запись создастся, но заработает, когда метод включат.
- Поиск дублей — только чтение `mdl_user`; ничего не сливается и не блокируется.
- Ядро и тема не патчатся; страницы — свои, макет `login`. На курсе с форсированной
  темой (236/238) форма сама рисуется в `theme_kabacademy`.

## Внешние зависимости

- `auth_kabmagic` ≥ 1.1.0 (жёсткая зависимость в `version.php`):
  `manager::issue_link()` выдаёт ссылку для письма существующему аккаунту. Плагин
  выключен или аккаунт не подпадает под его правила → письмо со страницей входа.
- `local_kabgender` (мягкая): пол по имени. Нет плагина — пол просто не проставится.
- ipinfo.io по HTTPS (с web-18 открыт, ответ ~0,15 с), таймаут 5 с. Недоступен —
  город останется пустым, флаг `geo` не ставится, запись не страдает.
- Cron Moodle — для фоновой задачи `after_signup`.
- Почта Moodle (на проде SendGrid). Письма уходят с `X-SMTPAPI`-категориями
  `moodle-signup`, `course-<id>` и, если есть, `camp-<метка>`; письмо о дубле —
  `moodle-dupalert`.

## Безопасность

- Рейт-лимит по адресу и IP (как в `auth_kabmagic`), honeypot-поле против ботов
  (заполнено → молчаливый редирект на «спасибо», ничего не создаётся).
- Запись доступна только для курсов из белого списка; для остальных — нейтральный
  ответ без названия курса.
- Страницы «спасибо» берутся только из настроек (админских); параметр `camp` —
  лишь ключ выбора, open redirect через него невозможен.
- Автовход не выдаёт существующие аккаунты (см. «Решения»). Оговорка: по чужому
  свободному адресу можно создать аккаунт и оказаться в нём залогиненным — аккаунт
  пустой, письмо с паролем уходит настоящему владельцу адреса; так работает любая
  регистрация без подтверждения, и так же работала WP-воронка.
- Пароль новичка: 10 символов из `random_int` (без похожих `0/O`, `1/l/I`); при
  включённой политике паролей — ядро `generate_password()` с проверкой политикой.
  Пароль нигде не хранится в открытом виде — только хеш в `mdl_user` и текст письма.
- UTM-параметры чистятся (`PARAM_NOTAGS`, 255 симв.) и уходят только на
  админские URL «спасибо».

## Установка без CLI (dataroot не писабелен, PHP в вебруте не исполняется)

1. Залить каталоги под юзером сайта (из LF-исходников; с Windows — через `tar`):
   ```bash
   tar -C public/public/local -czf /tmp/local_kabsignup.tgz kabsignup
   scp /tmp/local_kabsignup.tgz web-18:/tmp/
   ssh web-18 "tar -C /sites/edu.kabacademy.com/public/public/local -xzf /tmp/local_kabsignup.tgz && rm /tmp/local_kabsignup.tgz"
   ```
   Вместе с ним обновить `auth/kabmagic` (нужна версия ≥ 1.1.0, там новый
   `issue_link()`).
2. Установка через локальный HTTP:
   ```bash
   ssh web-18 "curl -s -H 'Host: edu.kabacademy.com' -H 'X-Forwarded-Proto: https' 'http://127.0.0.1/admin/index.php?confirmrelease=1' | grep -o 'status-new[^<]*<[^>]*>[^<]*'"
   ```
   — `status-new` должны быть `local_kabsignup` и апгрейд `auth_kabmagic`; затем тот же
   URL с `&confirmplugincheck=1&cache=0` — создаст таблицу и зарегистрирует задачу.
3. Заполнить «Курсы с открытой записью» (без этого любая ссылка отвечает «запись
   не ведётся») и токен ipinfo: Администрирование → Плагины → Локальные плагины →
   Запись на курс. На dev — SQL-ом в `mdl_config_plugins` (`plugin = 'local_kabsignup'`)
   **до** шага 2.
4. Проверка: открыть `/local/kabsignup/index.php?id=<курс>&camp=test` гостем,
   записать тестовый адрес; смотреть `mdl_local_kabsignup_log` (через минуту —
   `flags`), `mdl_user` (phone1, city, country), `mdl_user_enrolments` и письмо
   (на dev писем нет — `noemailever`, проверять по строкам в БД).

## Диагностика

```sql
-- заявки по кампаниям за 30 дней
SELECT campaign, status, COUNT(*) FROM mdl_local_kabsignup_log
 WHERE timecreated > UNIX_TIMESTAMP() - 30*86400
 GROUP BY campaign, status ORDER BY campaign, status;
-- последние заявки
SELECT id, courseid, userid, newuser, campaign, status, flags, ip, FROM_UNIXTIME(timecreated)
  FROM mdl_local_kabsignup_log ORDER BY id DESC LIMIT 20;
-- фоновые задачи, которые ещё не отработали (или падают)
SELECT id, FROM_UNIXTIME(nextruntime), faildelay, customdata FROM mdl_task_adhoc
 WHERE classname LIKE '%kabsignup%';
```

Письмо не пришло: смотреть `status` в журнале, затем условия `auth_kabmagic`
(метод аккаунта не в списке, аккаунт заблокирован) и `noemailever`/`divertallemailsto`.
Город пустой, `flags` без `geo`: IP частный (локальный тест) или ipinfo не ответил.

## Грабли

- **Курс нового набора надо добавить в «Курсы с открытой записью»** — иначе ссылки
  кампании молча отвечают «запись не ведётся» (та же грабля, что фильтр курсов
  у `local_kabfeedbackgdoc`). И в `TARGET_COURSE_IDS` отчёта о второгодниках.
- **На dev заявка с новым адресом отвечает 504 через 60 секунд — это не плагин.**
  `auth_edwiserbridge` синхронно шлёт события `user_created` и
  `user_enrolment_created` в WordPress (`wpsiteurl = https://dev.kabacademy.com`),
  а туда с dev-VM не достучаться — прокси обрывает ответ по таймауту. Сама запись
  дозавершается в фоне (аккаунт, зачисление, журнал, письмо), человек просто не
  видит «спасибо». На проде WP доступен, мост быстрый — задержки нет.
- **После выкладки новой версии фоновые задачи до 3 минут могут идти старым кодом**:
  процесс cron живёт `cron_keepalive` (180 с) и подхватывает новые adhoc-задачи с уже
  загруженными классами. Проверять поведение задачи — на заявках, сделанных через
  3+ минуты после выкладки (на dev 09.11 так «сломалась» проверка дублей).
- Админ и преподаватель курса по ссылке записи не записываются — сразу «спасибо»
  (это предпросмотр, а не баг).
- Настройки кэшируются: правка `mdl_config_plugins` SQL-ом без сброса кэша не
  подействует (на проде — только через UI; установка сама сбрасывает кэш).
- `thanks.php` показывает название курса только для курсов из белого списка.
- Поиск дублей использует MySQL-функции (`SUBSTRING_INDEX`, `REPLACE`, `RIGHT`) —
  на другой СУБД проверка молча пропускается.
- После апгрейда Moodle проверить, что каталог жив и плагин не «missing from disk».
